Each file is an idempotent, self-contained Supabase migration: it may alter tables/columns/constraints and then CREATE OR REPLACE FUNCTION(s) exposed as RPC endpoints. Internal layering by concern:
- Schema migrations: `supabase_checkout_migration.sql` (nullable `orders.user_id`, `postal_code`, atomic `create_checkout_order` with stock locking via `FOR UPDATE`), `supabase_seller_shipping_payment_migration.sql` (`sellers.cod`/`advance_pay_full`/`advance_pay_dc` flags plus CHECK constraints).
- Seller order surface: `supabase_seller_orders_rpc.sql` adds courier/tracking columns to `seller_orders`, enables RLS on `seller_orders`/`order_items`/`orders`, and exposes `get_seller_orders` (paginated, status-filtered, ILIKE search), `get_seller_order_detail`, and `update_seller_order_status`.
- Analytics surfaces: `supabase_seller_overview_rpc.sql` defines a two-phase load (`get_seller_overview_kpis` Phase 1 + `get_seller_overview_details` Phase 2) plus RLS policies; `supabase_seller_last_7_days_rpc.sql` provides `get_seller_last_7_days` with daily breakdown via `generate_series`.
- Wallet/commission domain: `supabase_wallet_payout_rpc.sql` creates three new tables (`seller_commission_monthly_cycles`, `seller_payments`, `seller_commission_cycle_items`) with indexes and RLS, plus helper `get_previous_month_year` and RPCs for wallet KPIs, commission submission transaction, paginated history, and lazy-loaded payment detail.
Dependency direction is one-way: RPCs read/write existing `orders`/`order_items`/`products`/`seller_orders` tables and never import each other — each script is independently deployable.
